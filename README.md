# release-lines-lab

Песочница, где на живом git проверены три вещи, которые предлагается сделать
с релизными линиями фронтенда. Код заглушечный, задачи вымышленные (`#100xx`),
никаких внутренних адресов и данных.

Все транскрипты в [`docs/transcripts/`](docs/transcripts) — это реальный вывод команд,
не пересказ.

## Топология

Пять линий, как в жизни: одна активная разработка, три релизные и одна LTS,
отрезанная раньше и потому сильно разошедшаяся.

```
main  (4.26.10.0)
 ├── releases/v4.26.9.0   отрезана позже всех
 ├── releases/v4.26.8.0
 ├── releases/v4.26.7.3   активно принимает фиксы
 └── lts/v4.0.17          отрезана ДО рефакторинга shared/*
```

Ключевая деталь: `refactor: extract shared table primitives (#10030)` переносит
`src/shared/table.js` в `src/shared/ui/table/primitives.js` **после** отреза LTS.
Именно это и создаёт расхождение, из-за которого порты в LTS дороже.

Пересобрать историю с нуля: `node build-history.mjs <папка>` (скрипт лежит рядом
с репозиторием, в исследовательской папке).

## 1. Порт: почему CHANGELOG конфликтует всегда и как это снимается

**Без `.gitattributes`** — [транскрипт](docs/transcripts/01-port-conflict-changelog.txt):

```
$ git cherry-pick -x main   # fix: show full message text in log table (#10080)
Auto-merging CHANGELOG.md
CONFLICT (content): Merge conflict in CHANGELOG.md
exit code: 1
```

Причём принесённый кусок тащит за собой чужие секции `# 4.26.9.0` и `# 4.26.8.0`,
которых в этой линии быть не должно — человек руками выбирает одну строку из шести.

**С одной строкой в `.gitattributes`** — [транскрипт](docs/transcripts/02-port-clean-with-union.txt):

```
CHANGELOG.md merge=union
```

```
$ git cherry-pick -x main   # fix: keep filter state on refresh (#10090)
Auto-merging CHANGELOG.md
[releases/v4.26.7.3 128d372] fix: keep filter state on refresh (#10090)
exit code: 0
```

Запись легла ровно под `# 4.26.7.3` целевой линии. Конфликтных файлов ноль,
маркеров ноль. `union` — встроенный драйвер git, локальной настройки не требует
и работает и на merge, и на cherry-pick.

**Что union НЕ решает** — [транскрипт](docs/transcripts/03-port-conflict-code-lts.txt).
Когда одну и ту же функцию правили независимо в двух линиях, конфликт настоящий:

```
$ git cherry-pick -x main
Auto-merging CHANGELOG.md            <- склеилось
CONFLICT (content): Merge conflict in src/shared/table.js
```

Заодно проверено и опровергнуто одно опасение: **переезд файла cherry-pick переживает.**
Git распознаёт переименование и кладёт правку в старый путь LTS сам —
`src/shared/ui/table/primitives.js` на main и `src/shared/table.js` на LTS
он сопоставляет без подсказок. Настоящие конфликты дают пересекающиеся правки
одних строк, а не сами по себе переезды.

## 2. Merge-forward: автомерж вверх по линиям

Порядок цепочки в [`.release-lines.json`](.release-lines.json). LTS в цепочку
не входит намеренно — он в `manual`, там порт остаётся cherry-pick'ом.

Инструмент — [`scripts/merge-forward.mjs`](scripts/merge-forward.mjs):
`--from` без флагов делает сухой прогон через `git merge-tree`, с `--apply --push`
идёт по цепочке до конца или до первого конфликта.

Локальный прогон — [транскрипт](docs/transcripts/04-merge-forward-local.txt):

```
цепочка: releases/v4.26.7.3 -> releases/v4.26.8.0 -> releases/v4.26.9.0 -> main
releases/v4.26.7.3 -> releases/v4.26.8.0: смерджено (4 коммит(ов))
releases/v4.26.8.0 -> releases/v4.26.9.0: смерджено (7 коммит(ов))
releases/v4.26.9.0 -> main: смерджено (10 коммит(ов))
```

В CI то же самое по триггеру `push` в `releases/**` —
[`.github/workflows/merge-forward.yml`](.github/workflows/merge-forward.yml).

Чистый прогон, [транскрипт](docs/transcripts/05-merge-forward-ci-clean.txt):
вся цепочка пройдена и запушена за четыре секунды, три линии обновились сами.

Конфликтный прогон, [транскрипт](docs/transcripts/06-merge-forward-ci-conflict.txt):
бот откатил merge и открыл [PR #1](https://github.com/creatoff/release-lines-lab/pull/1)
со списком конфликтных файлов.

### Что выяснилось по ходу

- **YAML нужен на каждой линии, инструмент — нет.** `push` триггерит воркфлоу
  из файла *пушнутой* ветки, поэтому `.github/workflows/merge-forward.yml` приходится
  портировать на все линии. А сам скрипт живёт в одном экземпляре на `main`:
  воркфлоу делает `checkout` main и передаёт линию параметром.
- **Правам нужно разрешение отдельно.** Первый конфликтный прогон упал на
  `GitHub Actions is not permitted to create or approve pull requests`.
  Лечится настройкой репозитория, не YAML. В ADO ровно тот же класс проблемы:
  build-идентити нужно право «Contribute to pull requests».
- **Push от `GITHUB_TOKEN` не триггерит воркфлоу повторно** — поэтому цепочка
  проходится внутри одного прогона, а не каскадом запусков. Так и надо.
- **Сухой прогон оптимистичен.** Он проверяет каждый шаг против текущего состояния
  цели, не учитывая предыдущий merge цепочки. Для оценки годится, для гарантии — нет.

### Цена, которую видно

После merge-forward на `releases/v4.26.8.0` в CHANGELOG сверху осталась пустая
секция `# 4.26.7.3`, а записи фиксов легли под `#### New Features` версии 4.26.8.0.
Это и есть обещанная «причёска раз в релиз»: union не конфликтует, но и не думает.

## 3. Версия из ветки и тег в момент публикации

`package.json` держит `0.0.0-dev` **во всех линиях** — файл одинаковый, значит
merge его не касается. Настоящая версия выводится
[`scripts/resolve-version.mjs`](scripts/resolve-version.mjs) по приоритету
`APP_VERSION` → имя ветки → `git describe` → `0.0.0-dev+<sha>`:

```
main                     0.0.0-dev+ea46722   (источник: заглушка + sha)
releases/v4.26.7.3       4.26.7.3            (источник: имя ветки)
releases/v4.26.8.0       4.26.8.0            (источник: имя ветки)
lts/v4.0.17              4.0.17              (источник: имя ветки)
```

Имя артефакта собирается из неё же:
`primo-rpa-orchestrator-ui-4.26.7.3-linux.zip`. Это важная деталь для переноса:
в настоящем пайплайне версия читается из `package.json` и попадает в имена архивов,
поэтому обнулить её в одиночку нельзя — пайплайн должен брать версию из того же
источника.

[`.github/workflows/publish.yml`](.github/workflows/publish.yml) — прототип доставки:

1. `build` — чекаутит выбранную линию, считает версию, **фиксирует SHA в output**
   и собирает артефакт;
2. `approve` — окружение `release-approval` с обязательным ревьюером, ручной гейт;
3. `tag` — ставит аннотированный тег `v<версия>+build.<номер>` на **тот SHA,
   который зафиксировали в п.1**.

Разрешать имя ветки повторно на шаге тега нельзя: она к моменту аппрува могла
уехать — от этого тег и защищает. Имя с номером сборки нужно потому, что одна
и та же версия может публиковаться дважды.

## Что здесь НЕ проверялось

- Стоимость разового примирения линий, накопивших встречные cherry-pick'и.
  История здесь собрана заново и такого груза не имеет.
- Ворота PR (обязательный ревьюер, блокирующая сборка) — сознательно вне объёма.
- Поведение на объёме реального репозитория: тысячи файлов, месяцы расхождения.
